# 要望まわりのUX修正・導線集約・公開シフト表のメモ表示（Ver.2.6.0）

Ver.2.5.0 のリリース後、運用者から6点の指摘を受けて対応した。

## 対象と変更内容

### 1. 要望を送れるのはスタッフだけにした

**指摘**: 管理者や開発者からも要望を送れるのが変。

- `components/FeedbackModal.tsx` — 本部管理者向けの分岐を削除し、スタッフ前提に単純化
- `components/AppMenu.tsx` — 「要望を送る」は `user.role === 'staff'` のときだけ出す
- `app/api/feedback/route.ts` — POST で `session.role !== 'staff'` を403で拒否

**理由**: 管理者・本部管理者は要望を受け取って対応する側で、自分宛てに送る導線があるのは不自然。
UIで隠すだけでなくAPIでも検証する（直接叩かれた場合に備える）。

**トレードオフ**: 管理者がアプリ自体の不具合を報告する手段がアプリ内から無くなった。
今のところ管理者＝運用者本人なので問題にならないと判断したが、
運用者以外が管理者になる場合は再考が必要。

### 2. 「店長」という語を全廃

**指摘**: 「店長へ」ではなく「管理者へ」に。このアプリでは「店長」は禁止語。

- UI（`FeedbackModal`）・ヘルプ（`lib/help/content.ts`）・SQLコメント
  （`supabase/schema.sql` / `supabase/migrations/2026-08-14_feedback.sql`）・`CHANGELOG.md` から全廃
- `CLAUDE.md` に「ロール名はスタッフ／店舗管理者（管理者）／本部管理者で統一。『店長』は使わない」を明記

適用済みマイグレーションのコメントも直しているが、SQLの意味は変えていない（再適用不要）。

### 3. 要望の状態を「未対応 / 対応済み」の2つに整理

**指摘**: 対応済みにした後も「既読にする」のような表示が残るのがおかしい。

**原因**: タブの振り分けが `status === 'new'` か否かだったため、
「既読にしただけ（`read`）」の要望が**対応済みタブに並んでしまっていた**。
状態は3つ（未読・既読・対応済み）あるのに、タブは2つで境界がズレていた。

- `app/s/[storeSlug]/admin/feedback/page.tsx` — タブを `done` かどうかで分けるよう変更。
  操作は「対応済みにする」1つに統一し、対応済みからは「未対応に戻す」で戻せるようにした
- `components/NavBar.tsx` — 件数バッジの集計を `status = 'new'` から `status != 'done'` に変更し、
  受信箱のタブの件数と一致させた

DBの3状態（`new` / `read` / `done`）はそのまま残している。画面上は `done` かどうかだけで扱う。

### 4. 公開シフト表に日付ごとのメモを表示

**指摘**: ログインしないで見れるシフト表にメモを入れておいてほしい。

- `supabase/migrations/2026-08-15_public_memos.sql`（新規・**要手動適用**）— `get_public_memos` RPC
- `supabase/schema.sql` — 同内容をベースラインにも反映
- `app/s/[storeSlug]/public/schedule/page.tsx` — RPCで取得し、既存の `memos` prop に渡すだけ
  （`TableView` / `TimelineView` は元から `memos` を受け取れる）

**★方針の転換★** Ver.2.3.0 では「コメント欄・メモは表示しない（不特定多数に見えるべきでない
私的な内容のため）」と明示して作った。運用側の要望により**意図的に覆している**。
URLを知っていれば誰でもメモを読めるため、**メモに個人的な内容を書かない運用が前提**になる。
シフトごとの `comment` は引き続き公開しない（こちらは方針を変えていない）。

RPCは `app_settings` のうち `memo_YYYY-MM-DD` のキーだけを返す。
提出期間（`period_*`）や時給（`wage_*`）は返さない。
キーの日付部分は `date` にキャストしていない（不正なキーが1行でも紛れるとキャスト例外で
クエリ全体が落ちるうえ、WHERE句の評価順序は保証されないため「正規表現で弾いてからキャスト」も
安全と言い切れない）。`YYYY-MM-DD` は辞書順と日付順が一致するので文字列のまま範囲比較している。

### 5. 使い方・要望・更新履歴を1か所に集約

**指摘**: 要望・更新履歴ボタンを配置する箇所は一か所にしたい。どこが良いか考えた上で。

**判断**: ヘッダー右上の「⋯」メニューに集約し、`components/AppFooter.tsx` は削除。

- `components/AppMenu.tsx`（新規）— 使い方 / 要望を送る（スタッフのみ）/ 更新履歴 + バージョン表示
- `components/NavBar.tsx` — ヘッダーの「?」を `AppMenu` に置き換え
- `app/admin/layout.tsx` — 本部ヘッダーにも `AppMenu` を追加（NavBarを使わないレイアウトのため）
- 3つのレイアウトから `AppFooter` を除去

**理由**:
- フッターは長いシフト表の一番下にあり、たどり着くのにスクロールが要る。
  「片手・数秒で使う」という前提（`docs/DESIGN_SYSTEM.md` §0）に合っていなかった
- 「困ったときに開く場所」がヘッダーの「?」とフッターの2か所に分かれていた
- ヘッダーのボタン数は増えていない（「?」を「⋯」に置き換えただけ）

**トレードオフ**: 使い方を開くのに1タップ増えた。導線が1か所になる利点を優先した。

### 6. 更新履歴をスタッフ向けの表示に

**指摘**: 更新履歴はスタッフが読む前提なので、技術的な内容（ファイル名とか）を隠して、
構造的に見やすいデザインに。

- `components/ReleaseNotes.tsx` — 表示前に2つのルールで絞り込む
  1. **インデントされた入れ子の箇条書きは出さない**（＝開発者向けの補足の置き場）
  2. **バッククォートで囲んだ部分は消す**（ファイル名・識別子）
  加えて「詳細は〜を参照」の行を落とし、除去後に残る空括弧・余分な空白を整える
- 見出し（追加 / 変更 / 修正）を色分けしたラベルとして表示し、種類が一目で分かるようにした
- `CHANGELOG.md` — 過去の全エントリを上記の約束に沿って書き直した
  （技術的な記述を入れ子の箇条書きへ移動）。冒頭に「書き方の約束」を明記
- `CLAUDE.md` — 同じ約束を追記

**設計判断**: 技術用語のブロックリストで消す方式は、キーワードが増えるたびに漏れるので採らなかった。
「CHANGELOG側の書き方の約束」と「表示側の2ルール」を対応させることで、
機械的で予測可能な絞り込みにしている。実際に全8エントリで、バッククォート・
ファイル拡張子・パス・RLS/JWT/RPC といった記述が残らないことを確認済み。

## 在庫管理アプリ（DB共有）への影響

## 追記: メニューの表示不具合（Ver.2.6.1）

**症状**: ヘッダー右上のメニューを開いても中身が見えない。「使い方」も開けない。

**原因**: ヘッダーに `backdrop-filter`（Tailwindの `backdrop-blur`）が掛かっていた。
`backdrop-filter` は子孫の `position: fixed` に対する**包含ブロック**を作るため、
ヘッダー内に置いた `fixed inset-0` のオーバーレイがビューポートではなく
**ヘッダー（高さ52px）を基準に配置**され、中身が潰れていた。

Ver.2.6.0 で導線をフッターからヘッダーへ移した際、それまで `NavBar` 直下（ヘッダーの外）に
あって正常だった `HelpModal` も一緒にヘッダー内へ移してしまったため、ヘルプも巻き込まれた。

**対応**: メニュー本体・`HelpModal`・`FeedbackModal` を `createPortal` で `body` 直下に描画。
あわせてアイコンを「⋯」からハンバーガー（≡）へ変更した。

**教訓**: `backdrop-filter` / `filter` / `transform` が掛かった要素の中に
`position: fixed` のオーバーレイを置かない。ヘッダーやツールバーの中にモーダルを持たせるなら
ポータルで `body` 直下へ逃がすこと。同じ罠が無いか他の `backdrop-blur` 箇所も確認済み
（シフト申請画面のモーダル類は別階層なので影響なし）。

## 追記: 要望の置き場を宛先ごとに分けた（Ver.2.7.0）

**指摘**: 管理者宛ての要望を確認できない。管理者と開発者で要望の表示が共有されるのを分配したい。

### 「確認できない」の実際の原因

不具合ではなく、**表示するデータが片方のタブに寄っていた**ことによる誤解だった。
「管理者へ」宛て2件がどちらも `done` で、既定の「未対応」タブが空だった。
権限まわりは実機と同じJWTを作って検証し、店舗管理者の権限でも
送信者名の埋め込みJOIN込みで正しく取得できることを確認済み。

ただし「片方のタブが空だと何も無いように見える」のは設計の落ち度なので、
**空表示にもう一方の件数を出し、そこから切り替えられるようにした**。
あわせて、取得エラーを握りつぶしていた箇所（`error` を捨てていた）を画面に出すよう修正。
「0件」と「読めていない」が区別できない状態だった。

### 宛先ごとの分配

- **店舗の受信箱**（`/s/[storeSlug]/admin/feedback`）= `destination = 'store'`（管理者へ）
- **本部の受信箱**（`/admin/feedback`・新規）= `destination = 'dev'`（開発者へ・全店舗横断）

本部の受信箱には、店舗名・送信者・アプリバージョン・GitHub Issueへのリンクを出す。
本部管理エリアにナビ（店舗一覧 / 要望）を新設し、未対応件数のバッジを付けた。

**理由**: 同じ画面に両方の宛先が混ざると「誰が対応すべき要望なのか」が曖昧になる。
それぞれの画面に「ここに何が届くのか」を明記した。

RLSは変更していない（本部管理者は元から全要望が見える）。画面側で `destination` を
分けているだけ。店舗管理者から「開発者へ」宛てが見えないことはRLSで保証されており、
実機と同じJWTで0件になることを確認済み。

## 追記: 導線の整理・自動削除・ヘッダー再構成（Ver.2.8.0）

### 期限切れの調整依頼を自動削除

`app/api/admin/requests/cleanup/route.ts`（新規）を管理者の依頼管理画面の初回表示で呼ぶ。

- 募集中のまま日付だけ過ぎた依頼が残ると、**スタッフ側の未対応バッジが永久に減らず通知が意味を失う**
- 依頼を消してもシフト（`shifts`）は別テーブルなので残る。`shift_request_targets` は
  外部キーの `on delete cascade` で一緒に消える
- **「今日」はサーバー側で日本時間として求める**。クライアントから受け取ると端末の時計や
  改ざんで削除範囲が変わってしまう
- `shift_requests` のRLSは店舗一致で全操作を許可しており、スタッフでも delete できてしまう。
  そのため画面から直接消さず、`requireAdmin` を通した service role のAPIに寄せた

Vercel Cron も検討したが、`CRON_SECRET` の発行という運用者側の手順が増えるわりに、
「管理者が依頼管理を開いたとき」で実用上は十分と判断した。

### 対応済みの要望を削除できるように

`DELETE /api/feedback` を追加。**`status = 'done'` の行しか消せない**ようクエリ条件に含めている
（未対応を読まずに消すことを構造的に防ぐ）。消せる範囲はPATCHと同じくサーバー側で絞り、
本部管理者以外は「自店の `destination='store'`」のみ。画面側でも確認ダイアログを挟む。

### 「要望」をナビから設定の中へ

- `components/NavBar.tsx` — `adminNav` を4項目に戻し、未対応件数のバッジは「設定」に付ける
- `app/s/[storeSlug]/admin/settings/page.tsx` — 既存の「人件費予測」「アンケート管理」と
  同じ形のカードとして「要望」を追加（未対応件数つき）

**理由**: 要望は毎日開くものではない。シフト・依頼・スタッフと同じ高さに並べると重要度を取り違える。
既に人件費予測とアンケート管理が設定配下にある構成とも揃う。

### ヘッダーの再構成

**症状**: 本部管理者だと文字が重なる。スタッフでも店舗名が隠れる。

**原因**: ヘッダーに ブランドマーク / アプリ名 / 店舗名 / ユーザー名 / 本部管理へ戻る /
メニュー / ログアウト を全部横並びにしていた。店舗名（例:「CARVAAN Delicatessen 横浜高島屋」）は
`truncate` で潰れ、本部管理者では「本部管理へ戻る」が加わって破綻していた。

**対応**: ヘッダーに残すのは「今どの店舗を見ているか」だけにし、
ユーザー名・本部管理へ戻る・ログアウトは `AppMenu` へ移した。
狭い画面ではアプリ名「シフト管理」も省く（ブランドマークで識別できる）。

ログアウトが1階層下がるが、頻度が低く誤タップの影響が大きい操作なので、
`docs/DESIGN_SYSTEM.md` の優先順（①誤操作しない）にはむしろ沿う。

### 使い方の並びを画面構成に合わせた

人件費予測・アンケート管理・要望を「設定から開くもの」として整理し、
各セクションの手順1を「ナビの『設定』を開き、〜をタップする」に統一。
`docs/GUIDE.md` も同じ構成で再生成される。

### 本部の受信箱のIssueリンク位置

本文の下（操作ボタンと同じ行）から、種別・店舗名と同じ上部のバッジ列へ移した。
「どのIssueか」は本文を読む前に知りたい情報のため。
Issue未作成のものだけ、下部に「Issue未作成」と出す。
