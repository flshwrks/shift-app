# 要望まわりのUX修正・導線集約・公開シフト表のメモ表示（Ver.2.6.0）

Ver.2.5.0 のリリース後、運用者から6点の指摘を受けて対応した。

## 対象と変更内容

### 1. 要望を送れるのはスタッフだけにした

**指摘**: 管理者や開発者からも要望を送れるのが変。

- `components/FeedbackModal.tsx` — 本部管理者向けの分岐を削除し、スタッフ前提に単純化
- `components/AppMenu.tsx` — 「要望を送る」は `user.role === 'staff'` のときだけ出す
- `app/api/feedback/route.ts` — POST で `session.role !== 'staff'` を403で拒否

**理由**: 管理者・本部管理者は要望を受け取って対応する側で、自分宛てに送る導線があるのは不自然。
UIで隠すだけでなくAPIでも検証する（直接叩かれた場合に備える）。

**トレードオフ**: 管理者がアプリ自体の不具合を報告する手段がアプリ内から無くなった。
今のところ管理者＝運用者本人なので問題にならないと判断したが、
運用者以外が管理者になる場合は再考が必要。

### 2. 「店長」という語を全廃

**指摘**: 「店長へ」ではなく「管理者へ」に。このアプリでは「店長」は禁止語。

- UI（`FeedbackModal`）・ヘルプ（`lib/help/content.ts`）・SQLコメント
  （`supabase/schema.sql` / `supabase/migrations/2026-08-14_feedback.sql`）・`CHANGELOG.md` から全廃
- `CLAUDE.md` に「ロール名はスタッフ／店舗管理者（管理者）／本部管理者で統一。『店長』は使わない」を明記

適用済みマイグレーションのコメントも直しているが、SQLの意味は変えていない（再適用不要）。

### 3. 要望の状態を「未対応 / 対応済み」の2つに整理

**指摘**: 対応済みにした後も「既読にする」のような表示が残るのがおかしい。

**原因**: タブの振り分けが `status === 'new'` か否かだったため、
「既読にしただけ（`read`）」の要望が**対応済みタブに並んでしまっていた**。
状態は3つ（未読・既読・対応済み）あるのに、タブは2つで境界がズレていた。

- `app/s/[storeSlug]/admin/feedback/page.tsx` — タブを `done` かどうかで分けるよう変更。
  操作は「対応済みにする」1つに統一し、対応済みからは「未対応に戻す」で戻せるようにした
- `components/NavBar.tsx` — 件数バッジの集計を `status = 'new'` から `status != 'done'` に変更し、
  受信箱のタブの件数と一致させた

DBの3状態（`new` / `read` / `done`）はそのまま残している。画面上は `done` かどうかだけで扱う。

### 4. 公開シフト表に日付ごとのメモを表示

**指摘**: ログインしないで見れるシフト表にメモを入れておいてほしい。

- `supabase/migrations/2026-08-15_public_memos.sql`（新規・**要手動適用**）— `get_public_memos` RPC
- `supabase/schema.sql` — 同内容をベースラインにも反映
- `app/s/[storeSlug]/public/schedule/page.tsx` — RPCで取得し、既存の `memos` prop に渡すだけ
  （`TableView` / `TimelineView` は元から `memos` を受け取れる）

**★方針の転換★** Ver.2.3.0 では「コメント欄・メモは表示しない（不特定多数に見えるべきでない
私的な内容のため）」と明示して作った。運用側の要望により**意図的に覆している**。
URLを知っていれば誰でもメモを読めるため、**メモに個人的な内容を書かない運用が前提**になる。
シフトごとの `comment` は引き続き公開しない（こちらは方針を変えていない）。

RPCは `app_settings` のうち `memo_YYYY-MM-DD` のキーだけを返す。
提出期間（`period_*`）や時給（`wage_*`）は返さない。
キーの日付部分は `date` にキャストしていない（不正なキーが1行でも紛れるとキャスト例外で
クエリ全体が落ちるうえ、WHERE句の評価順序は保証されないため「正規表現で弾いてからキャスト」も
安全と言い切れない）。`YYYY-MM-DD` は辞書順と日付順が一致するので文字列のまま範囲比較している。

### 5. 使い方・要望・更新履歴を1か所に集約

**指摘**: 要望・更新履歴ボタンを配置する箇所は一か所にしたい。どこが良いか考えた上で。

**判断**: ヘッダー右上の「⋯」メニューに集約し、`components/AppFooter.tsx` は削除。

- `components/AppMenu.tsx`（新規）— 使い方 / 要望を送る（スタッフのみ）/ 更新履歴 + バージョン表示
- `components/NavBar.tsx` — ヘッダーの「?」を `AppMenu` に置き換え
- `app/admin/layout.tsx` — 本部ヘッダーにも `AppMenu` を追加（NavBarを使わないレイアウトのため）
- 3つのレイアウトから `AppFooter` を除去

**理由**:
- フッターは長いシフト表の一番下にあり、たどり着くのにスクロールが要る。
  「片手・数秒で使う」という前提（`docs/DESIGN_SYSTEM.md` §0）に合っていなかった
- 「困ったときに開く場所」がヘッダーの「?」とフッターの2か所に分かれていた
- ヘッダーのボタン数は増えていない（「?」を「⋯」に置き換えただけ）

**トレードオフ**: 使い方を開くのに1タップ増えた。導線が1か所になる利点を優先した。

### 6. 更新履歴をスタッフ向けの表示に

**指摘**: 更新履歴はスタッフが読む前提なので、技術的な内容（ファイル名とか）を隠して、
構造的に見やすいデザインに。

- `components/ReleaseNotes.tsx` — 表示前に2つのルールで絞り込む
  1. **インデントされた入れ子の箇条書きは出さない**（＝開発者向けの補足の置き場）
  2. **バッククォートで囲んだ部分は消す**（ファイル名・識別子）
  加えて「詳細は〜を参照」の行を落とし、除去後に残る空括弧・余分な空白を整える
- 見出し（追加 / 変更 / 修正）を色分けしたラベルとして表示し、種類が一目で分かるようにした
- `CHANGELOG.md` — 過去の全エントリを上記の約束に沿って書き直した
  （技術的な記述を入れ子の箇条書きへ移動）。冒頭に「書き方の約束」を明記
- `CLAUDE.md` — 同じ約束を追記

**設計判断**: 技術用語のブロックリストで消す方式は、キーワードが増えるたびに漏れるので採らなかった。
「CHANGELOG側の書き方の約束」と「表示側の2ルール」を対応させることで、
機械的で予測可能な絞り込みにしている。実際に全8エントリで、バッククォート・
ファイル拡張子・パス・RLS/JWT/RPC といった記述が残らないことを確認済み。

## 在庫管理アプリ（DB共有）への影響

**なし。** 新規関数 `get_public_memos()` の追加のみ。既存テーブル・既存関数・既存ポリシーは不変。
`grant ... on all tables` / `alter default privileges` は不使用。`npm run check:contract` は不要。
