# 本部管理者アカウントの管理画面と、要望バッジが消えない不具合の修正

## 対象

- `app/api/hq/admins/route.ts` / `app/admin/admins/page.tsx` / `lib/hqAdmins.ts`（新規）
- `tests/hqAdmins.test.ts`（新規・13件）
- `lib/feedbackEvents.ts`（新規）
- `components/HqNav.tsx` / `components/NavBar.tsx` / `app/s/[storeSlug]/admin/settings/page.tsx`
- `app/admin/feedback/page.tsx` / `app/s/[storeSlug]/admin/feedback/page.tsx`
- `lib/routes.ts` / `lib/help/content.ts` → `docs/GUIDE.md` / `app/guide/`

## 1. 本部管理者アカウントの管理

### 何が問題だったか

本部管理者は**データベースに直接入れるしか作る方法が無かった**。

- `app/api/admin/users/route.ts` の `parseUserPayload` は role を `admin` か `staff` にしか正規化せず、
  `hq_admin` を作る経路が存在しない
- スタッフ管理画面は店舗配下にあり `store_id` が必須。本部管理者は `store_id` が null なので一覧にも出ない

結果、**本部管理者は1人しか存在せず、増やすことも名前やPINを変えることもできない**状態だった。
これは2つの課題の前提条件になっていた。

- **O-1（運用担当者が1名）**: 2人目を置きたくてもUIから作れない
- **引き渡し**: 会社の担当者に本部管理者を発行できない（`docs/OPERATIONS.md` §13 の手順6）

### 作ったもの

本部管理のナビに「本部管理者」タブを追加し、一覧・追加・編集（名前/PIN）・削除ができるようにした。

**店舗のスタッフ管理とは別の経路（`/api/hq/admins`）にした。**
あちらは「店舗に属する人」を扱い店舗境界の判定が入り組んでいる。本部管理者は所属店舗を持たないため、
同じ経路に混ぜると分岐が増えすぎる。

### 歯止め

**本部管理者が0人になると、誰も本部管理画面に入れなくなる。**
店舗の追加も権限の発行もできず、復旧にはデータベースを直接触るしかない。そのため2つ置いた。

- **自分自身は削除できない** … 操作の途中で自分が締め出される
- **最後の1人は削除できない** … 全員消えると復旧手段が無くなる

条件は `lib/hqAdmins.ts` に切り出してテストしてある（APIの中に埋めるとテストできないため）。
画面側でもボタンを無効化し、理由を `title` で出している。1人だけのときは注意書きも表示する。

対象が本当に `hq_admin` かをサーバー側で確認してから書き込む。
`createAdminClient()` はRLSを見ないため、店舗スタッフのIDを渡して権限を書き換えられるのを防ぐ。

## 2. 要望のバッジが消えない不具合

### 原因

バッジは NavBar・HqNav・設定画面の3か所にあり、それぞれ Realtime で `feedback` の変更を拾って
数え直していた。ところが**「対応済みにする」はサーバー側の管理キーで更新するため、
購読しているクライアントに変更が届かない**。結果、バッジだけが古い件数のまま残っていた。

要望画面のリストが即座に「対応済み」に変わるのは、画面側で自分の状態を書き換えているためで、
DBの変更が伝わっているわけではなかった。

### 直し方

更新した画面から `window` イベントで合図を出し、バッジ側が聞いて数え直す形にした（`lib/feedbackEvents.ts`）。

**RLSポリシーを足してクライアント直接更新に変える案も検討したが、採らなかった。**
マイグレーションが必要になるうえ、この不具合はリロードすれば直る軽微なものだったため、
DBを触らずに閉じられる方法を選んだ。Realtime の経路はそのまま残してあるので、
他のタブ・他の端末からの変更は従来どおり反映される。

## 確認したこと

- テスト121件すべて成功 / `tsc --noEmit` OK / `check:guide` OK / `next build` 成功
- 本番DBに対して**実際に追加→削除まで通した**。`store_id` が null で作られること、
  操作の記録に `user.create` / `user.delete` が store_id なしで残ることを確認
- 1人だけのときに削除ボタンが無効化され注意書きが出ること、2人になると有効化されることを画面で確認
- テストで作ったアカウントは削除済み（本番は元の1件に戻してある）

## 残作業

- **本部管理者はまだ1人。** 画面から追加できるようになったので、2人目を置くかは運用の判断
- 権限の降格（`canDemoteHqAdmin`）は関数だけ用意して未使用。
  本部管理者を店舗管理者に降格する導線は今回作っていない
