# アプリ全体の総点検（2026-09-11）

機能が増えてきた区切りとして、アプリ全体を4つの役割で点検した。

| 役割 | 担当 | 観点 |
|---|---|---|
| 機能監査 | サブエージェント | 3ロールそれぞれの業務が本当に終わるか。同種サービスに本質的に負けないか |
| セキュリティ監査 | サブエージェント | 致命的な穴・リスク |
| UI/UX監査 | サブエージェント | 視認性・導線・迷わなさ |
| 全体統括 | 本セッション | 指摘の**検証**・重複排除・優先順位付け・実装 |

3つの監査は並列で実施。統括側は**完了報告を信用せず、影響の大きい指摘を全て現物で確認**した
（過去に並列エージェントの中途半端な成果物を掴んだ経緯があるため。
`improvement_list/2026-08-08*` / メモリ `feedback-verify-parallel-agent-output`）。

## 統括役による検証の結果

**33件の指摘（機能12・セキュリティ5・UI/UX16）のうち、影響の大きい14件を現物で確認した。13件は事実、1件は前提が誤り。**

### 誤りだった指摘（採用せず）

**「店舗削除の確認が、何が失われるかを伝えていない（巻き込み削除の危険）」**
→ `app/api/hq/stores/route.ts:104-110` に**スタッフが1人でもいれば削除できない**制約が既にある。
巻き込み削除は構造的に起こらない。指摘の前提が誤っており、重大度「大」は成立しない。
ただし「確定してからエラーで気づく」導線ではあるので、**削除できない条件を確認画面に先に書く**
という小さな改善に読み替えて採用した。

### 監査役が見落としていた点（統括側で追加）

- **「店長」の語がドキュメントに1件残っていた**（`docs/OPERATIONS.md:95`）。
  UI/UX監査は `app/` `components/` `lib/` しか grep しておらず「0件」と報告していた
- **本番データとの突き合わせ**（エージェントはDBに触れない）。これが最大の発見につながった

## 最大の発見: 交代の仕組みが「使えない向き」に付いている

**「代わってほしい」は必ずスタッフ側から始まる。ところが調整依頼を作れるのは店舗管理者だけ。**

- 作成UI（`ShiftRequestModal`）は管理者の2画面からしか呼ばれていない
  （`admin/requests/page.tsx:304`, `admin/schedule/page.tsx:452`）
- スタッフ側は受ける／断るだけ（`staff/requests/page.tsx`）
- ヘルプも「管理者に相談してください」とアプリの外へ誘導（`lib/help/content.ts:63`）

そして **`npm run stats` の実績は、5か月・シフト544件に対して調整依頼 0件**。

機能が足りないのではなく、**現実の出来事の向きと機能の向きが逆なので一度も起動しない**。
実態はLINE等アプリの外で回っているはず。**機能の有無ではなく向きの問題**であり、
「あったら便利」ではなく「あるのに使われていない」という、最も直すべき種類の欠陥。

### 「交代募集を作らない」の記録（再検討を繰り返さないため）

5か月・シフト544件に対して調整依頼0件という事実を踏まえたうえで、
**LINEで回す**という判断。二重運用の混乱の方が高くつくという読み。

**この判断を覆す条件**: 多店舗化してLINEグループが店舗をまたいで肥大化したとき。
先送りするほど移行コストは上がる（`improvement_list` のこの行を根拠に再提案してよい）。

### FN-9 の設計判断（2026-09-11）

**深夜営業は扱わない。** 受付時間帯は 0:00〜24:00 の範囲で店舗ごとに設定でき、
**終了は最大24:00**（日またぎなし）。既定は従来どおり 8:00〜22:00 なので既存店舗は無変更。

将来 深夜営業の店が出た場合: `shifts.start_time`/`end_time` は**テキスト型**で
`timeToMinutes('26:00')` は正しく 1560 を返すため、**保存形式を変えずに**26時表記へ広げられる。
`lib/businessHours.ts` の冒頭にも同じことを書いてある。

## 判断が要るもの（判断前の記録）

### 1. ⚠️ 要望の送信先を非公開リポジトリに変える（最優先・運用作業）

コード側は警告表示まで。**置き場所そのものは変わっていない。**
手順は `docs/OPERATIONS.md` §5-5。**済むまでスタッフに「開発者へ」を案内しないこと。**

現時点でスタッフの記述は1件も流出していない（既存Issue 6件は開発者本人のテスト投稿）。

### 2. シフトのコメントが同僚全員に見える

`staff/schedule` は `isAdmin` を渡さず、コメントは無条件表示
（`TableView.tsx:204`, `TimelineView.tsx:305`, `ShiftDetailModal.tsx:72`）。

**ただしこれは 2026-08-25（v2.9.2）に意図して入れた機能**「シフト表のコメントを
時間帯の下に本文表示する」の結果。**仕様か事故かは作った人にしか判断できない。**

判断の材料: ログイン不要の公開シフト表では、コメントを
「私的なメモが不特定多数に見えるのを避けるため」意図的に除外している（`schema.sql:535`）。
**「コメントは私的たりうる」という判断は既にあるのに、ログイン済み同士には適用されていない。**

- 仕様なら → ヘルプに「同僚にも見えます」と明記する（小）
- 事故なら → 本人と管理者だけに絞る（小・3コンポーネントに条件追加）

### 3. スタッフ発の交代募集（前掲・最大の発見）

既存の `shift_requests` を流用でき、承認を挟む設計にすれば野良の代行も防げる。規模は中（2〜3日）。
**やらない判断も成立する**（LINEで回っているなら二重運用の混乱の方が高くつく）。
ただし多店舗化するとLINEグループが肥大化し、先送りするほど移行コストが上がる。

### 根本原因として記録しておくもの

**UX-12: 設計書が規定する共通コンポーネントが存在しない。**
`components/UI.tsx` / `Ledger.tsx` / `Feedback.tsx` はいずれも無く、
`buttonClass` / `ConfirmDialog` / `StickyBar` の定義も0件。各画面が個別に手書きしている。

UX-5（確定ボタンが4通り）・UX-10（色の揺れ）・UX-11（`window.confirm` の混入）は、
**すべてこの1つの構造から出ている**。個別に直しても再発する。
設計書自身の「『この画面だけ特別だから手で組む』は、ほぼ必ず2画面目が現れる」がそのまま起きた。

## 良くできていると評価された点（壊さないこと）

- **調整依頼の二重承諾防止**: `status = 'open'` のときだけ更新する条件付きUPDATEで排他制御
- **前月コピー / 1日を複数日にコピー**: 繰り返し入力の負担を実質的に解消している
- **「まとめて提出」の状態遷移**: 位置と大きさを変えず結果だけ色で伝える（設計書どおり）
- **「別のアカウントでログイン中です」画面**: 黙って差し替えず、誰がログイン中かを示して選ばせる
- **シフト種別を専用ページに分離**: 年に数回しか触らない設定を常時編集可能にしない判断
- **設定画面の管理メニュー**: 新しい配色を持ち込まず、ヘルプと同じ色の言語で種類を見分けさせる
- **RLSの一貫性**: 全テーブルで店舗境界が適用され、`using` だけで `with check` が無いポリシーは無い
- **`store_id` の強制導出トリガー**: 他店の `user_id` を指定したなりすましINSERTを構造的に防ぐ
- **「店長」の排除**: コード側は完全に徹底されていた
