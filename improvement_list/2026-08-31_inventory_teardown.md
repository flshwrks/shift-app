# 在庫管理アプリとのDB同居を解消（F-9 の解消）

## 対象

- 本番Supabase: 在庫管理アプリの `inv_*` オブジェクト30個を削除（作業は `inventory-app` 側）
- `CLAUDE.md`: 「★このDBは在庫管理アプリと共有している★」→「DBの同居はもう無い」に置き換え
- `app/api/hq/stores/route.ts`: 店舗削除時の在庫データチェックを削除
- `supabase/schema.sql`: 共有前提の★コメント4箇所を書き換え
- `docs/OPERATIONS.md`: §1 / §2 / §3 / §7 / §8 / §9 / §12 F-9 / §13-1 を更新

## 変更内容

**在庫管理アプリを廃止し、このDBをシフト管理アプリ専用にした。**
シフト管理アプリのオブジェクトは一切変更していない（削除対象は `inv_` プレフィックスのみ）。

コード側で消えたのは1箇所だけ。`app/api/hq/stores/route.ts` の店舗削除ガードで、
`inv_items` / `inv_stock_transactions` に行が残っている店舗の削除を拒否していた部分。
このチェックは「テーブルが無ければ黙って飛ばす」実装だったため、
`inv_*` の削除で自動的に無効化されており、残しても死んだ分岐にしかならない。
**スタッフが残っている店舗を削除できない制約はそのまま**なので、うっかり削除の防止は効いている。

`docs/OPERATIONS.md` は共有を前提にした記述が広範囲にあったため、まとめて更新した。
特に影響が大きいのは次の3点。

- **§3**: `SUPABASE_JWT_SECRET` が「在庫アプリと同じ値。両方同時に更新する」ではなくなり、
  単独でローテーションできるようになった
- **§8 / §9**: バックアップから復旧しても他アプリを巻き込まなくなった
- **§13-1**: 移管手順の前提が変わり、**プロジェクトをそのまま移すだけ**になった。
  データ移行が不要なので、移管当日にシフト管理アプリを止める必要がない
  （全員の再ログインも暗証番号の再発行も発生しない）

`npm run check:contract`（在庫アプリ側の共有依存チェック）への参照も外した。

## 理由

会社への引き渡しにあたり、Supabaseプロジェクトの所有権を移す必要が出た。
在庫管理アプリが同じプロジェクトに相乗りしていたため、そのままでは
「在庫アプリのデータごと会社に渡る」か「分けた瞬間に在庫アプリが止まる」のどちらかになる。

在庫アプリの本番データは26行（試用時のもの）で業務では使われていなかったため、
別プロジェクトへ移す（認証と店舗マスタの作り直しで数日）のではなく廃止を選んだ。
判断の詳細は `inventory-app/improvement_list/2026-08-31_teardown.md`。

## 効果

- **F-9 が解消**（在庫管理アプリとJWT署名鍵・Supabaseプロジェクトを共有している）
- 在庫アプリ側に未対策として残っていた
  「在庫アプリのトークンでシフトデータが読める」経路も消滅
- 情報システム部門向けの技術審査で、「なぜ別アプリと鍵を共有しているのか」を
  説明する必要がなくなった

## 確認したこと

- テスト63件すべて成功 / `npm run check:guide` OK / `next build` 成功
- 削除後、本番でログインが通ることを確認済み
- 削除後に `users` / `stores` / `list_login_users` / `is_hq_admin` が残存していることをSQLで確認

## バージョン

利用者から見える挙動は変わらないため、バージョンは上げていない
（消したチェックは `inv_*` の削除で既に到達不能になっていた）。
