# 全社展開に向けたセキュリティ・運用体制の診断と、初期対応

## 対象

- `docs/OPERATIONS.md`（新規）— 運用ハンドブック
- `README.md` — create-next-app のひな形からプロジェクトの入口に置き換え
- `.env.local.example` / `.gitignore` — 必須変数の欠落と、ファイル自体が未追跡だった問題を修正
- `package.json` / `package-lock.json` / `.github/workflows/ci.yml` — 依存更新と脆弱性検査の自動化
- 成果物（アプリ外）: 経営層向け「全社展開の判断材料」／情シス向け「シフト管理アプリ 技術審査票」

## 背景

「将来的に全社へ展開することを想定したとき、セグメントとして課題になるセキュリティと、
特定個人に属人化しない管理体制を、社内に説得できる形にしたい」という依頼。
説得相手は経営層と情報システム部門の両方で、資料は分けて作る方針とした。

## 診断の結論

**技術的な欠陥で全社展開を止めるべきものは無い。条件は体制側にある。**

- 店舗間のデータ遮断はRLSでDBに強制されており、アプリの不具合では破れない。
  PINはbcrypt＋5回ロック、管理キーはサーバー限定、SECURITY DEFINER関数はPUBLICからもrevoke済み。
  監査の記録が事故1件を含めて `docs/SECURITY.md` に残っている
- 一方、**アカウント・鍵・知識・本番反映の権限がすべて1人に集中**している（O-1）。
  店舗が増えるほど、この1人の不在が「不便」から「業務停止」に変わる

指摘は9件（重大2・要対応5・低2）＋運用2件。重大の2件は次のとおり。

- **F-1: 開発者ログインが4桁の共有パスワード1つ**（`DEV_LOGIN_PASSWORD`）。
  `POST /api/dev-login` は試行回数の制限も記録も無く、通過すると全店舗を横断できる
  `developer` ロールのセッションが出る。利用者のPINには5回ロックがあるが、この経路には無い
- **F-2: 発行済みセッションを失効させられない**。`GET /api/session/token` はCookieだけを根拠に
  Supabase用JWTを再発行し、利用者がDBに存在するかを確認していない。
  退職者を削除しても最大30日は閲覧でき、現状の遮断手段は `SESSION_SECRET` 変更（全員強制ログアウト）のみ

## 今回実施した対応

### 1. 依存の脆弱性を解消し、再発を検知できるようにした（Ver.2.9.3）

`npm audit --omit=dev` が high 5件（Proxy/Middlewareのバイパス、RSCのキャッシュポイズニング、
`ws` のメモリ開示ほか）。`next` 16.2.4 → 16.3.3、`@supabase/supabase-js` 2.104 → 2.112 で 0 件になった。
CIに `npm audit --audit-level=high` を追加。

Proxyバイパス系の指摘は、`proxy.ts` を認可の最終防衛線にしていない設計のため実害は限定的だが、
多層防御の1層が崩れた状態を放置しない判断で取り込んだ。

### 2. 引き継ぎに必要な情報をリポジトリに入れた

- `docs/OPERATIONS.md`: 構成／アカウント台帳（要記入）／鍵の一覧とローテーション／権限の棚卸し／
  人の出入り／リリースと切り戻し／DB変更手順／バックアップ／障害対応／定期作業／引き継ぎ／リスク登録簿
- `README.md`: create-next-app のひな形のままで、クローンしても何のアプリか分からなかった
- **`.env.local.example` が `.gitignore` の `.env*` に巻き込まれてリポジトリに入っていなかった。**
  さらに必須の `SESSION_SECRET` と `SUPABASE_SERVICE_ROLE_KEY` が記載されておらず、
  この通りに設定しても起動しない状態だった（＝新しい担当者は自力で環境を作れない）。
  `!.env*.example` で除外を解除し、2変数を追記した

### 3. 説得用の資料を2本作成した

経営層向けは「結論 → できていること → 3つの穴 → 投資 → 3段階の計画 → 決めてほしいこと3点」。
情シス向けは6領域の点検票（対応済17／指摘9／要確認3）と指摘事項の詳細。
**確認できなかった項目（契約プラン・リージョン・管理者の人数）は推測せず「要確認」として残した。**

## 残作業

第1段階（全社展開の前提条件）は未着手。F-1 と F-2 は環境変数の変更やDB照合を伴うため、
本番の設定変更とセットで計画する必要がある。

1. **F-1**: `DEV_LOGIN_PASSWORD` を長いランダム値へ変更（Vercelと`.env.local`の同時更新）。
   本番では既定で無効にし、試行回数の制限と成否の記録を追加する
2. **F-2**: `/api/session/token` で利用者の存在とロールをDB照合する。
   さらに `users` にセッション世代を持たせて個別失効できるようにする
3. **F-3**: 追記専用の監査テーブル。書込みは `service_role` 経由のAPIに集約されているので記録点は少ない
4. **F-5**: Supabaseのプラン確認 → RPO/RTO決定 → 復旧を一度試す。
   **在庫管理アプリと同一DBのため、巻き戻すと在庫データも巻き戻る**点の合意が要る
5. O-1: アカウントの会社名義化と2人目の担当者（会社側の意思決定）

## 補足

- リスクの番号（F-1〜F-9 / O-1〜O-2）は `docs/OPERATIONS.md` と技術審査票で共通。片方だけ振り直さないこと
- `docs/SECURITY.md` は「監査の記録」、`docs/OPERATIONS.md` は「日々の運用と引き継ぎ」で役割を分けた。
  F番号で相互に参照できるようにしてある
