# システム移管手順の文書化

## 対象

- `docs/OPERATIONS.md`（§13「システムの移管（所有者が変わるとき）」を追加）

## 変更内容

運用ハンドブックに、**アカウントの所有者そのものを移す**ときの手順を新設した。
既存の §11 は「人」の引き継ぎ（新しい担当者のオンボーディング）を扱っていたが、
GitHub / Vercel / Supabase の所有権を個人から組織へ移す手順は、どこにも書かれていなかった。

追加した内容:

- **13-1**: 在庫管理アプリとのDB共有をどう扱うか（A: まとめて移す / B: DBを分ける）
- **13-2**: 事前準備のチェックリスト
- **13-3**: 当日の作業順（DB → リポジトリ → 実行環境 → 鍵 → アクセス先 → アプリ内権限 → 旧環境停止）
- **13-4**: シークレット6つの入れ替え方と影響範囲
- **13-5**: 移管完了の判定条件（§11 の完了条件と同じ4項目を実演してもらう）

## 理由

移管を実際に始めてから調べると必ず止まる。特に次の2点は、当日に気づくと作業が終わらない。

1. **Supabaseプロジェクトを在庫管理アプリと共有している。**
   確認したところ、両アプリは同一のプロジェクトURLと**同一の `SUPABASE_JWT_SECRET`** を使っていた
   （リポジトリ直下 `CLAUDE.md` に記載のとおり）。
   このまま所有者を移すと在庫アプリのデータごと移る。
   **契約・移管の日程を決める前に方針を確定させる必要がある**ため、手順の冒頭に置いた。

2. **順番を間違えると全員がログインできなくなる。**
   `SESSION_SECRET` の入れ替えを実行環境の用意より先にやると、その時点で全セッションが無効化される。
   順番そのものが手順の中身なので、表形式で固定した。

また、移管後に旧所有者が鍵を知っている状態を残さないため、
「新しい値は移管先の担当者がその場で生成する」を明記した。

## 追記（同日）— 13-1 を書き直した

当初は「A: まとめて移す / B: シフト管理のDBを分ける」の二択で書いていたが、
在庫管理アプリが実質稼働していないことが分かったため、前提から見直した。

**動かすのは在庫管理アプリのほうで、シフト管理アプリは据え置く**、という形に変更。
シフト側を動かすと全員の再ログインと暗証番号の再発行が発生するが、
在庫側はほぼ空なので動かしても失うものがない。移管当日の工程がダウンタイムゼロになる。

在庫アプリ側の結合の実態も調べて明記した。

- `inv_*` から `public.stores` / `public.users` への**外部キーが11本**
- ログインは `verify_login` / `list_login_users` に完全依存
- `inv_*` オブジェクトは30個（テーブル・ビュー・RPC）

このため「別プロジェクトへ移す」は認証と店舗マスタの作り直しを伴い、数日かかる。
稼働していないアプリにその工数を払う合理性がないので、**廃止を推奨**とした。
`supabase/migrations/*.sql` は在庫アプリのリポジトリに残るため、実装自体は失われない。

副次的に、F-9（JWT署名鍵の共有）と
`inventory-app/docs/RUNBOOK.md` §6 の「在庫アプリのトークンでシフトデータが読める」
が両方とも消える。§12 の F-9 の記述も更新した。
