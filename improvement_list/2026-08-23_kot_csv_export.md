# KING OF TIME スケジュールCSV出力の追加

## 背景

店舗の勤怠管理に KING OF TIME を使っているが、その月の出勤予定（スケジュール）を
KOTの管理画面で**毎月手入力**している。シフト管理アプリで確定したシフトがあるのだから、
そこからCSVを作って一括登録できるようにしたい、という要望。

## 調査結果（要点）

KOT には標準機能として「スケジュールデータ［CSV］」の一括インポートがある。
オプション契約・追加費用・API利用申請は不要。

決め手は **CSVの列構成をKOT側の「入力レイアウト」で自由に定義できる**こと。
アプリがKOTの固定フォーマットに合わせるのではなく、**KOTをアプリの出力に合わせられる**ため、
アプリは1種類の並びだけ出せばよい。必須項目も「勤務日」「従業員コード」の2つだけ。

制約（実装に反映済み）:

- 1ファイル10,000件まで / 取込日の3ヶ月前〜1年1ヶ月後のみ
- 従業員コード・パターンコードは半角英数3〜10文字
- 勤務日は `yyyyMMdd` か `yyyy/MM/dd`、時刻は「対象日HH:mm」（当日は省略可）
- 既存スケジュールがある日は更新扱い

詳細な出典・API方式との比較・ヒアリング項目は `docs/KOT_INTEGRATION.md` に集約した。

## 変更内容と、その判断理由

### 設定の保存先に専用テーブルを作らず `app_settings` を使った

従業員コードは本来 `users` の列にするのが素直だが、**このSupabaseプロジェクトは在庫管理アプリと
共有しており**（`CLAUDE.md`）、`users` に手を入れるのは静かに向こうを壊すリスクがある。
`app_settings(store_id, key)` は時給（`wage_<user_id>`）で既に同じ使い方をしている前例があり、
RLSも「SELECTは店舗スコープ、書込は管理者のみ」で要件を満たす。
**マイグレーション0本**で収まるので、こちらを選んだ。

キー: `kot_code_<user_id>` / `kot_pattern_<shift_type>` / `kot_date_format` /
`kot_output_mode` / `kot_code_digits` / `kot_include_off` / `kot_include_draft` / `kot_header`

### 出力方式を「パターンコード＋予定時刻」の併用を既定にした

- パターンコードだけだと、アプリの「カスタム」シフト（時刻が毎回違う）を表現できない
- 予定時刻だけだと、KOT側の勤務区分・集計区分が決まらず、「休み」も表現できない

両方出せばKOT側で予定時刻がパターンの時刻を上書きするので、A〜Gもカスタムも1つの形式で通る。
どちらか片方しか受け付けない設定のKOTもありうるので、3択で切り替えられるようにした。

### ゼロ埋め桁数を設定項目にした

KOT側の従業員コードが `007` なのに `7` を渡すと「該当する従業員がいない」系のエラーになり、
桁数が原因だと気づきにくい（実運用での既知の躓きどころ）。数字だけのコードにのみ適用する。

### BOMを付けずに出力する

ExcelでUTF-8保存すると先頭にBOMが付き、KOT側が1列目のタイトルを認識できず失敗する。
`Blob` に BOM を足さない実装にしたうえで、画面とヘルプに
「ダウンロードしたCSVをExcelで開いて保存し直さない」を明記した。

### Web API 方式は採らなかった

KOT には `PUT /v1.0/daily-schedules` でスケジュールを登録できるWeb APIもあるが、

1. アクセストークン発行時に**接続元IPアドレスの登録が必要**で、Vercel（動的IP）から素直に叩けない
2. 長期資格情報を1つ増やすことになる
3. 利用禁止時間帯（8:30〜10:00 / 17:30〜18:30）やレート制限の考慮が要る

月1回・1〜2分の作業を自動化する対価としては重い。複数店舗で毎月やるのが負担になった時点で再検討する。

### `/simplify` で入れた整理

- **月タブ生成の共通化**: `buildMonthTabs()` を人件費予測とKOT連携で二重に持っていたので `lib/shifts.ts` に移した。
  起点となる月だけ引数で変えられる（人件費は2ヶ月前から、KOTは1ヶ月前から）
- **設定の保存形式を `lib/kot.ts` に寄せた**: 読み取り（`parseKotSettings`）だけがlib側にあり、
  真偽値を `'1'`/`'0'` にする書き込み側は画面に直書きされていた。対になる `serializeKotSetting()` を追加し、
  保存形式を知っているのはlibの2関数だけにした
- **桁数上限の一元化**: `10` が4箇所に散っていたので `KOT_MAX_CODE_DIGITS` と `clampKotCodeDigits()` にまとめた
- **設定取得の直列を解消**: 出力設定・パターンコードはスタッフ一覧に依存しないのに `users` の取得を待っていた。
  effectを2つに分け、`users` を待つのは従業員コードの取得だけにした（画面表示までの往復が1回減る）

見送ったもの: `app_settings` のupsert（4ファイル7箇所で同じ形。今回の差分の外まで触ることになるため）、
blobダウンロードの共通化（`lib/useTableExport.ts` と合わせて2箇所目。3箇所目が出たら切り出す）。

### 2026-08-23 追記: 一次ヒアリングの回答

- KOTに入れているのは**予定だけ**（実績は店頭の打刻）。休憩の予定入力なし、日跨ぎ勤務なし
  → **懸念していた追加実装（休憩・日跨ぎ）はいずれも不要になった**
- **パターン（勤務区分）が全社共通で他店舗のぶんも大量にあり、一覧から選ぶのが面倒**というのが
  手入力の負担の中身だった。CSV取り込みはコードを直接指定するのでこの手間が丸ごと消える＝効果が大きい。
  ただし*自店で使っているパターンコードの特定*が新たな論点になった
  → 大量の一覧から探させるのではなく、**入力済みの月をエクスポートして逆引きする**方針
  （`docs/KOT_INTEGRATION.md` §4-B 2通目）。それも難しければ「予定時刻のみ」出力で回避できる

これを受けて `lib/kot.ts` の警告を2段階に分けた。パターン未設定でも
「予定時刻＋パターン」モードなら行自体は出せるので、
**行が落ちる場合だけ error、時刻だけで出せる場合は warn** にした（以前は一律 error で誤解を招いた）。

### 2026-08-24 追記: 管理画面の実物確認で方針確定

KOT管理画面のスクリーンショットで確認（詳細は `docs/KOT_INTEGRATION.md` §4-C）。

- **「スケジュールデータ［CSV］」は表示されている** → 権限のブロッカーはクリア
- **エクスポートのボタンが1つも無い** → 「入力済みの月を出して逆引き」案は使えない
- **パターンコードが入っているのは全18件中の最初の8件だけで、残りは空欄。**
  自店で使っていそうな 10:15 始まりの時間帯がまさにコード未設定側にある。
  さらにパターン名が「10:15-18:15」のように**時刻そのもの**で、勤務区分としての意味を持っていない
- 従業員コードは **`000` と `1592` が混在**していて桁数が揃っていない

→ **`outputMode = 'time'`（予定時刻のみ）で運用する。**
パターンコードを使わないので、コード未設定の問題も「大量の一覧から選ぶ手間」も同時に消える。
アプリのA〜GとKOTパターンの対応表という作業自体が不要になり、カスタムシフトもそのまま出せる。
**ゼロ埋めは 0（桁揃えしない）**にすること（4桁に揃えると `000` が壊れる）。

残る未確認: 従業員コードの全員分 / 「入力レイアウト」を新規作成できるか /
出勤所属コード（複数所属のスタッフがいる場合に列の追加が要る）
