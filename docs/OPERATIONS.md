# 運用ハンドブック（引き継ぎ・体制）

> このアプリを**特定の個人がいなくても運用し続けられる**ようにするための資料。
> 「何がどこで動いていて、誰が鍵を持っていて、壊れたら何をするか」を1か所にまとめる。
>
> 対になる資料: 設計と脅威モデルは `docs/SECURITY.md`、データモデルは `docs/SPEC.md`、
> 利用者向けの操作は `docs/GUIDE.md`。**この3つは既に揃っている**ので、
> ここでは運用（人・鍵・手順）だけを扱う。
>
> ⚠️ **「要記入」と書いてある箇所は、現時点で確定していない**。
> 全社展開の前にここが埋まっていることが条件になる。

## 1. 全体構成

| 層 | 使っているもの | 置き場所 |
|---|---|---|
| アプリ本体 | Next.js（App Router） / React / Tailwind CSS | GitHub `flshwrks/shift-app` |
| ホスティング | Vercel（プロジェクト名 `shift-app`） | `master` への push で本番デプロイ |
| データベース | Supabase（PostgreSQL + Realtime） | **在庫管理アプリと同一プロジェクトを共有** |
| 認証 | 独自のhttpOnly署名Cookie＋そこから派生するSupabase JWT | Supabase Auth は使っていない |
| CI | GitHub Actions（`.github/workflows/ci.yml`） | push/PR時に audit・ドキュメント整合・型・ビルド |

**押さえておくべき性質**

- 本番デプロイは `master` への push だけで起きる。ステージング環境は無い（要検討事項、O-2）
- DBのマイグレーションは**自動適用されない**。`supabase/migrations/*.sql` を人がSupabaseの
  SQL Editorに貼って実行する。**コードとDBの適用順序を間違えると全員ログインできなくなる**（§7）
- **DBは在庫管理アプリと共有している**。`users` / `stores` / ログイン系RPC / RLSヘルパー関数を
  向こうが参照している。詳細と禁止事項は `CLAUDE.md` の「★このDBは在庫管理アプリと共有している★」

## 3. シークレット一覧

すべて Vercel の環境変数と、開発者の手元の `.env.local` にある。**リポジトリには入っていない**
（`.gitignore` で `.env*` を除外済み）。新しい担当者が環境を作るときは `.env.local.example` を参照。

| 変数 | 用途 | 漏れたときの影響 | ローテーション |
|---|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | RLSを完全に無視してDBを読み書きする管理者キー | **最大**。全店舗の全データが読み書きされる | Supabaseダッシュボードで再発行 → Vercelと`.env.local`を更新 |
| `SUPABASE_JWT_SECRET` | Supabase用JWTの署名鍵 | 大。任意の権限のJWTを偽造できる | **在庫管理アプリと同じ値。変えるなら両方同時に更新する** |
| `SESSION_SECRET` | セッションCookieの署名鍵 | 大。任意の利用者になりすませる | 変更すると**全員が再ログイン**になる（緊急遮断の手段でもある。§5） |
| `DEV_LOGIN_PASSWORD` | 開発者ログイン（全店舗横断の最高権限） | 大 | Vercelの環境変数を変えるだけ。**24文字以上のランダム値にすること**（未満だとAPIが503で開かない） |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 公開前提の匿名キー | 小（RLSで保護されている） | 通常不要 |
| `GITHUB_TOKEN` | 要望をGitHub Issueにする（任意） | 小（Issues権限のみ） | GitHubで失効・再発行 |

**鍵が漏れたと疑ったときの順番**

1. `SUPABASE_SERVICE_ROLE_KEY` を再発行 → Vercelを更新 → 再デプロイ
2. `SESSION_SECRET` を変更（全セッションが無効化される）
3. `SUPABASE_JWT_SECRET` を変更する場合は**在庫管理アプリと同時**に行う
4. Supabaseのログで、漏洩期間中の不審なアクセスを確認する
5. 経緯を `docs/SECURITY.md` に追記する（過去のインシデントも同じ形で記録してある）

## 4. 権限モデル

| ロール | 範囲 | 作り方 |
|---|---|---|
| `hq_admin`（本部管理者） | 全店舗。店舗の作成・削除 | DBで直接 `role` を変更（画面からは作れない） |
| `admin`（店舗管理者） | 自店のみ | 本部管理者または店舗管理者がスタッフ画面から設定 |
| `staff`（スタッフ） | 自店のみ | 店舗管理者がスタッフ画面から追加 |
| `developer` | `hq_admin` と同格 | DBに保存されない。`DEV_LOGIN_PASSWORD` を知っていれば誰でもなれる |

店舗間のデータ遮断は**DBのRLSで強制**されている（アプリのクエリ条件だけに頼っていない）。
ただし `SUPABASE_SERVICE_ROLE_KEY` を使うAPIルートはRLSを迂回するため、
**そこだけはアプリコードが唯一の防壁**になる（`docs/SECURITY.md`「店舗境界の実体はコードにある」）。

### 棚卸し（四半期ごと）

- [ ] `hq_admin` の一覧を出し、現在もその権限が必要な人だけか確認する
- [ ] 各店舗の `admin` の人数を確認する（店舗あたり2人以上いるか＝店長不在時に回るか）
- [ ] 退職者・異動者が残っていないか確認する（削除すればログイン状態も切れる）
- [ ] `developer` を使った人がいたか確認する（Vercelの実行ログに `[dev-login]` として出る）
- [ ] 「操作の記録」で、権限変更・スタッフ削除・暗証番号の再発行に心当たりのないものが無いか確認する

## 5. 人の出入り

### 入るとき

1. 店舗管理者が「スタッフ管理」から追加し、PINを発行する
2. PINは口頭または個別に伝える（画面から再表示はできない。忘れたら再発行）
3. 店舗のログインURL（QRコード）を伝える

### 店舗が変わるとき

スタッフは**掛け持ちできない**設計。異動は「元の店舗で削除 → 新しい店舗で追加」になる。
**過去のシフト実績は削除時に一緒に消える**（物理削除）。実績を残す必要がある場合は、
削除前に該当月のシフト表を画像保存しておくこと。

### 辞めるとき ⚠️

1. 店舗管理者が「スタッフ管理」から削除する
2. **削除するとログイン状態も切れる**（2026-08-31 対応済み）。
   管理操作は即座に、データの閲覧も最長45分（次のトークン更新まで）で止まる。
   その端末は自動的にログイン画面へ戻り、「アカウントが削除されたか、権限が変更されました」と表示される
   - **より早く確実に断ち切りたい場合**（端末の紛失、PINの漏洩など）は
     `SESSION_SECRET` を変更する。**全員が再ログインになる**が、その場で全セッションを無効化できる
   - 「特定の1人だけを即座に締め出す」機能はまだ無い（§12 の残作業）
3. 本部管理者・店舗管理者が辞める場合は、§2 のアカウント台帳の権限も外す

## 6. 変更を本番に出す手順

```
git checkout -b <作業ブランチ>              # master に直接コミットしない
# 変更する
npm test && npx tsc --noEmit && npm run build   # 手元で通してから
git push -u origin <作業ブランチ>           # → Vercelがプレビュー環境を作る
# プレビューURLで確認 → PR → CI通過 → master にマージ = 本番デプロイ
```

**壊れやすい中核には自動テストがある**（`tests/`）。実働時間の計算（休憩の控除）、
ログイン後の行き先、セッションCookieの検証、DB用トークンのクレーム——
**どれも壊れると業務が止まるか、権限の境界が破れる箇所**なので、
ここを変更したら必ず `npm test` を通すこと。CIでも同じものが走る。

- **バージョンとCHANGELOG**: 利用者に意味のある変更をしたら `package.json` の版を上げ、
  `CHANGELOG.md` の先頭に日本語で書く。これはアプリ内の更新履歴ページにそのまま出る。
  書き方の約束（スタッフが読んで分かる日本語だけをトップレベルに書く）は `CLAUDE.md` に定義済み
- **改修の経緯**は `improvement_list/YYYY-MM-DD_*.md` に1計画1ファイルで残す
- **ヘルプ**（`lib/help/content.ts`）を直したら `npm run gen:guide` を実行する。
  CIの `npm run check:guide` がズレを検出する

### 切り戻し

Vercelのダッシュボードで直前のデプロイを "Promote to Production" するのが最速（数十秒）。
**ただしDBのマイグレーションを伴う変更は、コードを戻してもDBは戻らない。** §7を参照。

## 7. DBを変更する手順

1. `supabase/migrations/YYYY-MM-DD_*.sql` を書く（**適用済みのファイルは編集しない。追加していく**）
2. `supabase/schema.sql` を最新の姿に合わせて更新する
3. **在庫管理アプリを壊さないか確認する**:
   `cd ~/.claude/在庫管理アプリ/inventory-app && npm run check:contract`
   （`users` / `stores` / `verify_login` / `list_login_users` / `jwt_*()` / `is_hq_admin()` を
   触った場合は必須。詳細は `CLAUDE.md`）
4. Supabase の SQL Editor に貼って実行する
5. **コードとDBの適用順序**を必ず設計する。過去に「先にRLSを絞って全員ログイン不能」に
   近い事故が起きうる構成だったため、`docs/SECURITY.md`「⚠️ 適用手順（順序厳守）」に前例がある

**新しい `SECURITY DEFINER` 関数を作ったら、`anon` / `authenticated` だけでなく
`public` からも明示的に revoke すること。** Postgresは関数作成時にPUBLICへEXECUTEを
自動付与するため、これを忘れると誰でも呼べる。過去に実際のインシデントが1件ある
（`docs/SECURITY.md` のインシデント記録）。

## 8. バックアップと復旧（要確認）

**現状、バックアップ方針が文書化されていない。全社展開の前に必ず決めること。**

- [ ] Supabaseのプランと自動バックアップの**保持期間**を確認する
- [ ] Point-in-Time Recovery（PITR）が使えるか確認する（有料プランの機能）
- [ ] **どこまで戻せれば許容できるか（RPO）／何時間で復旧すべきか（RTO）を決める**
      参考: シフト表は「翌月分を月末に作る」運用なので、1日分の損失でも
      店舗運営に直接響く。RPO 24時間は妥当な最低ライン
- [ ] 復旧を**実際に一度試す**（復旧手順は試したことがなければ手順ではない）
- [ ] 在庫管理アプリと同一プロジェクトのため、**復旧すると在庫データも一緒に巻き戻る**。
      両アプリの担当者で合意しておくこと

## 9. 止まったとき（一次対応とフォールバック）

**現状、エラー監視が入っていない（F-4）。異常は利用者からの申告で気づく。**

| 症状 | まず見る場所 |
|---|---|
| 画面が真っ白・500 | Vercel Dashboard → Deployments → Runtime Logs |
| 全員ログインできない | Supabaseの稼働状況、`SESSION_SECRET`・`SUPABASE_JWT_SECRET` の設定、直近のマイグレーション |
| 特定の人だけログインできない | PINの5回失敗ロック（15分で自動解除）。急ぐならPIN再発行 |
| データが見えない・他店のものが見える | RLSポリシー。**すぐに `docs/SECURITY.md` を持って調査する** |
| 「勝手にシフトを変えられた」と相談された | 設定 →「操作の記録」で、その日時の確定・変更を確認する |
| 表示が古い | Realtimeの購読切れ。再読み込みで直るか確認 |

**連絡経路（要記入）**: 一次受け → 二次受け → 業務側の判断者。
現状は事実上「利用者 → 恩田さん」の1本しかない。

### 9-1. 考え方

**このアプリが止まっても、店舗の営業は止めない。**
シフトは「すでに決まっていること」なので、確定済みの情報が手元にあれば紙で回せる。
復旧を急ぐより、**先に紙の運用へ逃がしてから直す**ほうが被害が小さい。

### 9-2. 症状ごとの対応

| 症状 | 影響 | すぐやること | 目安 |
|---|---|---|---|
| 画面が開かない（Vercel障害・デプロイ失敗） | 提出も閲覧もできない | Vercelのステータスを確認し、**直前のデプロイを Promote to Production で戻す**（数十秒） | 数分 |
| データベースが応答しない（Supabase障害） | ログインもデータ表示も不可 | Supabaseのステータスを確認。復旧待ちの間は**掲示してある紙のシフト表で運用** | 数十分〜数時間 |
| データが消えた・壊れた | 過去のシフトが失われる | Supabaseのバックアップから復元（§8）。**在庫管理アプリも一緒に巻き戻る**点の合意を先に取る | 数時間 |
| アカウントが使えない（支払い停止・凍結） | 全機能停止 | 別アカウント・別サービスへ移行（§9-4） | 数日 |
| 担当者が不在 | 変更も障害対応もできない | 後任がこのハンドブックとリポジトリを見て対応する | — |

### 9-3. 平常時にやっておくこと（フォールバックの本体）

**ここを怠らなければ、上のどのケースでも「営業が止まる」ことはない。**

1. **月に1回 `npm run backup` を実行する。** 全テーブルの中身がJSONで手元に落ちる。
   シフトを確定した直後（月末）が最適。**Supabaseごと失っても、このJSONがあればデータは残る**
   - 出力先は `backups/`（Gitには入らない設定にしてある）。**中身は全店舗の氏名・勤務予定・時給が平文**なので、保管場所に注意する
   - `users.pin_hash` は意図的に除外している。復元時は暗証番号を再発行する運用
2. **確定したシフト表を画像で保存し、店舗で印刷・掲示する。**
   これが最も強いフォールバックで、**システムが全部落ちてもその月の営業は回る**
3. **`supabase/schema.sql` を最新に保つ。** これがあれば、空のPostgreSQLに構造を作り直せる

### 9-4. 最悪ケースの復旧手順（クラウドを失った場合）

このアプリは特定の会社にしかない機能に依存していないため、丸ごと引っ越せる。

1. 新しいPostgreSQLを用意する（Supabaseの別プロジェクトでも、他社のマネージドPostgreSQLでも、自社サーバーでもよい）
2. `supabase/schema.sql` を適用し、続けて `supabase/migrations/*.sql` を**日付順に**適用する
3. `backups/<日付>/*.json` からデータを投入する。**順序は `stores` → `users` → `shifts` / `app_settings` →
   `shift_requests` → `shift_request_targets` → `surveys` → `survey_options` → `survey_responses` → `feedback`**
   （外部キーの依存順。逆順で入れると失敗する）
4. **暗証番号を全員分再発行する**（バックアップに含めていないため）
5. 環境変数を新しい接続先に差し替え、`npm run check:env` で漏れがないか確認する
6. ホスティングへデプロイする（Vercel以外でも動く。Node.jsが動く環境であればよい）

### 9-5. 復旧訓練

**半年に一度、9-3 の 1 と 9-4 の 1〜3 を実際にやる。**
手順は、試したことがなければ手順ではない。訓練の結果はこのファイルに追記する。
