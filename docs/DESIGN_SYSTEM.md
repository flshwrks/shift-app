# デザイン・仕様共通リファレンス

> シフト管理アプリと在庫管理アプリで共有する、店舗向けアプリの型。
> 他の店舗関係アプリを新規に作る際も、これをそのまま出発点にする。
>
> 「なぜこうなっているか」の理由も書いてあるので、コピーする時は理由ごと引き継ぐこと。
> 理由を無視して数値だけ変えると、次第に別物になっていく。
>
> **2026-08 改訂**: 全面的に見直した。旧版（白いカード＋コバルト青＋Tailwind既定色）は
> 一般的な管理画面テンプレートの型そのもので、業務用の道具に見えなかった。
> 改訂の経緯と却下案は各節の「なぜ」に残してある。

---

## 0. 前提 ─ 誰がどこで使うか

**ここを外すと、以下のすべての判断が意味を失う。**

- 使うのは**アルバイトを含む店舗スタッフ**。ITに詳しいとは限らない
- 端末は**自分のスマホ・縦持ち・片手**。厨房の照明、濡れた手、急いでいる
- 読む時間は**数秒**。じっくり眺める画面ではない
- 扱う情報は**ほぼ全部が数値**（在庫数・時間・件数）

したがって設計の優先順は **①誤操作しない → ②一目で分かる → ③速い → ④きれい**。
きれいさが先に来ることはない。

## 1. 技術スタックのデフォルト選定

| 項目 | 選定 | 理由 |
|---|---|---|
| フレームワーク | Next.js（App Router） | 最新の安定版を都度確認（`~/.claude/tech-versions.md` 参照） |
| 言語 | TypeScript（strict） | `any` を使わない |
| スタイリング | Tailwind CSS 4 | `@theme` でトークンを直接定義する |
| DB / BaaS | Supabase（PostgreSQL） | RLSでテナント境界を強制できる |
| デプロイ | Vercel | GitHub連携でpush即デプロイ |
| Lint | ESLint（**Reactフック規則のみ**） | 早期リターン後にフックを置いて画面が落ちる事故を実際に起こした。型チェックもビルドも通ってしまうため。**スタイル系のルールは足さない**（警告が増えると本当のエラーが埋もれる） |

## 2. デザイン原則

### 2.1 「AIが作った感」の正体は装飾ではなく構図

絵文字をやめる・色を変える、といった表層の対策では消えない。次の3つが本体。

1. **すべてが同じカードに入っている** — 情報の性質が違うのに入れ物が同じで、区別が消える
2. **色が装飾として常時鳴っている** — ブランド＝ボタン＝アクティブ＝リンクを1色が兼ねると、どれの意味も持てない
3. **数字が主役なのに主役に見えない** — 本文と同じ書体・同じ大きさで、白い箱の中に埋もれている

### 2.2 既定は罫線。ただしカードを禁止しない

**同種のものが並ぶとき**（一覧・履歴・明細）は罫線で区切る。
**独立した1つのものを置くとき**（ログインカード、モーダル、単独の要約ブロック、
大きな操作ボタン）はカードでよい。

| 罫線にする | カードにする |
|---|---|
| 在庫一覧・履歴・棚卸明細・結果表 | ログイン、モーダル／ボトムシート |
| 設定項目の並び | ダッシュボードの操作ボタン（独立した的） |
| 同じ形の行が続くもの | 品目詳細の見出しブロック（そのページの主題） |

> 旧版の問題は「カードを使ったこと」ではなく、**同一のカードが27箇所にあって
> 情報の性質の違いが消えていたこと**。入れ物が1種類しかないのが問題だった。
> 罫線を新しい唯一の入れ物にしたら、同じ失敗を繰り返すことになる。

### 2.3 ★ルールより使いやすさを優先する★

本節のすべては**既定値であって法則ではない**。
現場で使いにくくなるなら、そのルールのほうを曲げる。

判断に迷ったら **「厨房で片手・数秒」（§0）に照らして、どちらが速いか**で決める。
一貫性は手段であって目的ではない。

### 2.4 色は意味を持つときだけ出す（色の予算）

| 役割 | 色 | 使ってよい場所 |
|---|---|---|
| 骨格・文字・罫 | **無彩の墨** | それ以外すべて。**ここに色を入れない** |
| 行動 | **青1色** | 主ボタン／選択中タブ／リンク／フォーカスリング。**この4つだけ** |
| 警告・破壊 | **赤** | 削除・取消・危険な状態 |
| 状態 | 意味が固定された色 | 業務上の状態にだけ。装飾には一切使わない |

> 旧版は `blue-600` が27箇所にあった。色相を変えることより、**この削減のほうが効く。**
> Square も Stripe も青を使っているがテンプレートには見えない。骨格が無彩だから。

### 2.5 色だけで状態を伝えない

P型・D型の色覚特性では緑と赤が近づく。直射日光下でも色は飛ぶ。
**色 ＋ 位置（行頭の罫）＋ 短い文字**の3重にする。

### 2.6 数字は読み手に計算させない

**「1kg ／ 基準10 ／ 10%」ではなく「あと 9kg」と書く。**
前者は読み手に引き算をさせている。現場が知りたいのは差そのもの。
充足率のパーセントは飲食店の実務ではまず使われないので出さない。
足りているときは**何も出さない**（静かであることが「問題なし」の合図）。

### 2.7 見て終わる数字を置かない

「品目数 12件」のような、見ても何もできない数字をダッシュボードに置かない。
3枚並べると「それらしく見える」のが唯一の理由なら、それは装飾である。
出すのは**これから手を動かす対象**だけで、押したらその対象に絞り込まれること。

### 2.8 操作は使用頻度で重みを変える

検索・絞り込み・並べ替えを等価に4段積むのは「機能を思いついた順に並べた」だけ。
**常時出すのは最頻の1つ**。残りは畳む。

### 2.9 読む画面と記録する画面で言語を変える

- **読むとき**（一覧・履歴・結果）＝ 落ち着いて突き合わせる → **密度と整列**
- **記録するとき**（入力・棚卸し）＝ 片手・急ぎ → **大きさと明快さ**

同じカードで両方をやると、どちらにも最適化されない。

## 3. カラーパレット

`app/globals.css` の `@theme` で定義する。**色温度は寒色**に寄せる。

> 一度「帳簿の紙」としてベージュ寄りにしたが却下した。古い台帳の質感は出るが、
> 飲食の現場に必要な**清潔感と逆**になる。ステンレス・タイル・白衣の側に寄せる。

```css
@theme {
  --color-paper: #F4F7FA;   /* 地・帯 */
  --color-sheet: #FFFFFF;   /* 行の地 */
  --color-rule:  #E2E8ED;   /* 細罫（行間） */
  --color-rule-2:#C7D0D8;   /* 太罫（区切り） */

  --color-ink:   #10151B;   /* 本文  17.06:1 */
  --color-ink-2: #48535F;   /* 副文   7.29:1 */
  --color-ink-3: #67717D;   /* 補助   4.61:1 ← AA下限。これより薄い墨を本文に使わない */

  --color-ai-50: #E8F1FB;   /* 行動色の淡色 */
  --color-ai-600:#0A66C2;   /* 行動   白文字 5.69:1 */
  --color-ai-700:#08529E;   /* 行動・押下時 */

  --color-alert-600: #C62B1F; /* 警告・破壊  5.19:1 */
  --color-alert-700: #A32218; /* 警告・押下時 6.90:1 */

  /* 成功（保存できた・確定した）。状態色の緑と同値にして意味を1つに保つ */
  --color-ok-600: #0A7A4B;    /* 5.01:1 */
  --color-ok-700: #086139;    /* 6.63:1 */
}
```

**全色が地・面の両方で WCAG AA（4.5:1）を満たすこと。** 変更したら必ず再計算する。
旧版は Tailwind 既定色をそのまま使っていて、2色が AA 不合格だった。

### 意味が固定された色

業務上の意味を持つ色は、**テーマとは独立した定数**として `lib/types.ts` に置き、
インライン `style` で当てる（Tailwindクラスにしない）。テーマを変えても意味が変わらないように。

```ts
export const STOCK_LEVEL_COLORS: Record<StockLevel, string> = {
  out:   '#C62B1F',  // 5.19:1
  low:   '#A85207',  // 4.94:1
  ok:    '#0A7A4B',  // 5.01:1
  unset: '#67717D',  // 4.61:1
};
```

棚卸しの差異（`DIFF_COLORS`）、棚卸しの状態（`COUNT_STATUS_TICK_COLORS`）も同じ扱い。
**増（実地>理論）に行動色の藍は使わない** — 藍は下記4用途の予算に固定されており、
押せない数字に使うと「押せるもの」の目印が薄まるため、`#A85207` を当てている。

> 値が他の定数と一致していても、**意味が違うなら定数を分ける**。
> 「入力中は残りわずかと同じ色」という関係を作ると、片方を直したときにもう片方が黙って動く。

シフト管理アプリの `SHIFT_COLORS` も同じ扱い。**ヘルプ画面の早見表と実データの表示を必ず一致させる。**

### シフト管理アプリでの当て方

シフト管理アプリには `slate-*` / `blue-*` を使ったクラスが1000箇所以上ある。
1つずつ書き換えるのではなく、**`@theme` でスケールの定義そのものを上の値に差し替えている。**
既存のクラスを1文字も触らずに全画面が同時に移り、書き換え漏れがまだらな色として残らない。
`red` / `emerald` / `green` も、Tailwind既定値が小さい文字でAAを満たさないため同様に差し替えている。
角丸（`--radius-lg` 等）も同じ理由で 3〜6px に再定義している。
**新しく書くコードでは意味付きトークン（ink / rule / ai / alert / ok）を使うこと。**

## 4. 書体

**中身がほぼ数値のアプリなので、数字に書体を与えることが最も効く。**

```css
font-family:
  'Plex',                 /* 数字・英字のみ。unicode-range で日本語には当たらない */
  'Hiragino Sans',        /* Mac / iPhone。現場のスタッフはほぼこれ */
  'BIZ UDPGothic',        /* Windows 10/11 同梱。UD設計で游ゴシックより読みやすい */
  'Yu Gothic UI', Meiryo, 'Noto Sans JP', system-ui, sans-serif;

font-feature-settings: "palt";  /* 日本語の約物を詰める */
font-synthesis: none;           /* 合成太字を禁止（太字の前後で行が伸びる） */
```

### 数字だけWebフォント（IBM Plex Sans）

- **`unicode-range` で Latin と記号に限定する。** 日本語はシステムフォントのままなので、
  低速回線でも日本語の表示が待たされない
- 必要な文字だけに絞り込む（`pyftsubset`）。配布の latin サブセットは1ウェイト22KBだが、
  **107グリフに絞れば7.5KB**。3ウェイトで23KB
- 400 だけ `preload` する。500/700 は遅れてよい
- **日本語のWebフォント化は見送る。** 品目名は運用中に自由入力されるため使用文字を
  事前に絞れず、常用漢字を積むと1MB超になる。得られるのはWindows PCでの印象改善だけ
- **避ける書体:** Inter / Space Grotesk / Poppins ─ 生成物での使用が突出しており、
  それ自体が「らしさ」の記号になっている

### 数値の扱い

- 数量は**大きく・字間を締めて・単位は小さく添える**
- 桁が縦に並ぶ場所は必ず `tabular-nums`
- 太さは **400 / 500 / 700 の3段だけ**。中間を作らない

## 5. コンポーネントパターン

**まず `components/UI.tsx` と `components/Ledger.tsx` を見ること。**
画面側でクラス文字列を手書きしない。無ければ**キットに足す**（画面に一度きりの見た目を作らない）。

| 部品 | 置き場所 |
|---|---|
| `Button` / `buttonClass` / `TextLink` / `QtyInput` / `Field` / `Segmented` | `components/UI.tsx` |
| `Modal` / `BottomSheet` / `ConfirmDialog` / `StickyBar` / `Section` / `PageTitle` | `components/UI.tsx` |
| `Bleed` / `FilterBar` / `LedgerHead` / `LedgerGroup` / `LedgerList` / `LedgerBand` / `LedgerEmpty` | `components/Ledger.tsx` |
| `LevelTick` / `Figure` / `Shortfall` / `StockRow` | `components/Ledger.tsx` |
| `Badge` / `EmptyState` / `ErrorBanner` / `InfoBanner` / `WarnBanner` / `LoadingText` | `components/Feedback.tsx` |

> **「この画面だけ特別だから手で組む」は、ほぼ必ず2画面目が現れる。**
> 実際に入庫と出庫が同じ確定ボタンを別々に持ち、同じ「この画面だけ」というコメントまで
> 揃っていた。1画面目で気づいたらキット側を広げる。

以下は各部品が内部で使っている組み合わせ（キットを直すときの参照用）。

**罫線セクション**（カードの代わり）
```
bg-sheet border-y border-rule-2      ← 帯・見出し
bg-sheet border-b border-rule        ← 行
```
モバイルでは左右いっぱいに罫を伸ばす（`-mx-4 sm:mx-0`）。中途半端に余白を残さない。

**行**
```
flex items-stretch border-b border-rule
  → 行頭に 3px の状態罫（w-[3px] self-stretch）
  → 本文 pl-3 pr-3 py-2
```

**ボタン**（`Button` / `buttonClass`）
- 主: `bg-ai-600 text-white rounded-[3px] font-bold` ─ **有彩色にすること**
- 副: `bg-sheet border border-rule-2 text-ink rounded-[3px]`
- 破壊: `bg-sheet border border-alert-600 text-alert-600 rounded-[3px]`
- link: `text-ai-600 font-bold hover:underline` ─ 開閉トグルなど面を持たせないもの

サイズは `sm`(h-8) / `md`(h-10) / `lg`(h-12) / **`xl`(h-14)**。
`xl` は記録画面の確定ボタン専用（片手・厨房で押すため・§2.9）。
`success` を渡すと `bg-ok-600` になる。**位置も大きさも変えずに色だけで結果を伝える**
（ボタンが動くと、押した直後に次の操作を見失う）。

`<Link>` をボタンに見せたいときは `buttonClass({ variant, size })` を使う。
画面ごとに同じクラス文字列を再宣言しない。

> 主ボタンをモノクロ（墨）にする案は却下した。コントラスト比は最高（17.4:1）だが、
> **周囲の文字と同じ色なので前意識では拾えず、読んで探すことになる。**
> 「見たときに読めるか」（コントラスト）と「探さなくても目に入るか」（色相）は別の問題。
> 黒い主ボタンが機能するのはデスクトップ・広い余白・急いでいない場面に限られる。

**フォーム入力**
```
bg-sheet border border-rule-2 rounded-[3px] px-3 py-2 text-ink
focus:outline-none focus:border-ai-600 focus:ring-1 focus:ring-ai-600
```
スマホでフォーカス時にズームしないよう **16px を下回らせない**（`.no-zoom-input`）。
`.no-zoom-input` は `@layer base` に置いてある。素で書くと Tailwind のユーティリティと
同じ扱いになり、`text-[26px]` のような指定に競り勝ってしまうため。
数量欄は `QtyInput`（`fontPx` を渡す）を使い、この事情を画面側に持ち込まない。

**モーダル**（スマホはボトムシート、デスクトップは中央）
```
fixed inset-0 bg-ink/40 flex items-end sm:items-center justify-center z-50 p-4
→ 中身: bg-sheet rounded-t-lg sm:rounded-[4px] sm:max-w-lg shadow-xl
```

**固定フッター**（`StickyBar`）
```
fixed bottom-14 sm:bottom-0 left-0 right-0 p-3 bg-sheet/95 backdrop-blur border-t border-rule-2
```
`StickyBar` は**同じ高さのスペーサーを自分で出す**。呼び出し側に `pb-40` を対で
書かせる約束にしていたが、条件付きで出し分ける画面では必ず片方が抜ける。

**トーストは作らない。** フィードバックはインラインの帯＋ボタンのラベル遷移で表す。
**破壊的操作は必ず確認ダイアログを挟む**（`window.confirm` は使わない）。

## 6. アイコンとナビゲーション

- アイコンは `components/icons.tsx` に集約し、Lucide（ISC）のパスをコピーして使う。
  **手書き・絵文字は使わない**
- **アイコンで飾らない。** 見出しにアイコンを添えない。使うのは
  ナビゲーション・動作の区別（入庫／出庫）・状態の記号に限る
- **自明な装飾は置かない。** 行全体がタップできるならシェブロンは不要
- ブランドマークは「角丸2〜3pxの色付きボックス＋線画アイコン」。
  **2つのアプリを行き来するので、どちらにいるかの識別子は必要**（省略しない）

**ナビゲーション**
- スマホ: 画面下部固定のボトムナビ（アイコン＋短いラベル、アクティブは上端にインジケーター）
- デスクトップ (`sm:`以上): ヘッダー直下の横並びタブ
- **見出しを三重化しない。** アプリ名バー → タブ → ページ見出し と同じ語が並ぶなら、
  ページ見出しを削る
- 未対応件数・下書きありは小さな丸バッジ（数字は9+で省略）

## 7. 認証パターン（店舗スタッフ向けの簡易ログイン）

一般消費者向けSaaSのようなメール+パスワードは、現場のスタッフには不向き（メールアドレスを持たない/覚えていないスタッフがいる）。この系統のアプリでは以下を標準とする。

1. **名前選択 + 4桁PIN**。Supabase Authは使わず、独自のPIN認証にする
2. PINは **bcryptハッシュ化**して保存（固定ソルトのSHA-256等は絶対に使わない。過去に実際にインシデントを起こした手法）
3. ログイン失敗5回で一定時間ロックアウト
4. セッションは**httpOnly署名Cookie**（HMAC-SHA256、独自シークレット）。JSから読めない形で保持する
5. SupabaseのRLSでテナント境界を強制したい場合、Cookieセッションとは別に**短命なSupabase JWT**を発行し、`supabase-js`の`accessToken`コールバックに渡す（Supabase公式の「サードパーティ認証」パターン）。JWTは**localStorageに置かず、メモリ保持＋都度再取得**にする（XSS時の被害をTTL内に限定するため）

この構成の詳細な設計判断は `docs/SECURITY.md` を参照。

## 8. マルチテナント（複数店舗）パターン

「同一組織が複数店舗を運営し、本部が横断管理する」という業態のアプリで再利用できる型。

- 店舗テーブル（`stores`: id, slug, name）を用意し、あらゆる業務テーブルに `store_id` を持たせる
- ロールは3階層: 本部（全店舗、`store_id`はnull）／ 店舗管理者（自店のみ）／ スタッフ（自店のみ、掛け持ちなし）
- URLは `/s/[storeSlug]/...` の形で店舗を明示する（店頭QRコード運用と相性が良い）。本部は店舗に紐づかない別URL（例 `/admin/...`）
- 店舗間のデータ遮断は**RLSでDBレベルに強制**する。アプリ側のクエリ条件（`.eq('store_id', ...)`）だけに依存しない
- **service_roleクライアントはRLSを無視する**ため、管理者API（Route Handler）側でも必ず店舗スコープを検証すること。DBとアプリコードの二重チェックになる
- 詳細設計は `improvement_list/2026-08-08_multi_store_support.md` を参照（フェーズ分割の失敗例も記録してあるので、次回同種の移行をする際は必ず読むこと）

## 9. DB運用ルール

- マイグレーションはSupabase SQL Editorで**手動適用**するSQLファイルとして `supabase/migrations/YYYY-MM-DD_説明.sql` に置く（自動適用ツールは導入していない）
- `supabase/schema.sql` は「ゼロから新規構築する場合のベースライン」として、適用済みマイグレーションをすべて反映した最終形を常に保つ
- SECURITY DEFINER関数を新規作成する際は、**PostgresがデフォルトでPUBLICにEXECUTE権限を付与する**ことを必ず意識する。意図的に公開するRPC以外は `revoke ... from public, anon, authenticated` を忘れない（過去に実際にPINが書き換わるインシデントが発生している）

## 10. バージョン管理・ドキュメント運用

新しいアプリでも同じ4点セットを最初から用意する。

| ファイル | 役割 |
|---|---|
| `package.json` の `version` | Semantic Versioning。ユーザー向けの意味ある変更でインクリメント |
| `CHANGELOG.md` | バージョンごとの変更履歴（技術的な言い回しでよい） |
| `docs/GUIDE.md` | **全機能を集約した唯一の使い方マニュアル**。SPEC.md等に機能チェックリストを重複して書かない |
| `docs/SPEC.md` | 技術資料（データモデル・ルーティング）に専念。機能一覧はGUIDE.mdへ |
| `improvement_list/YYYY-MM-DD_説明.md` | 1プラン＝1ファイルで改修履歴を記録。対象・変更内容・理由を書く |

これらを更新するルールをプロジェクトの `CLAUDE.md` に明記しておくと、セッションが変わっても運用が続く（このアプリの `CLAUDE.md` を参照）。

## 11. コーディング規約

- コメントは「なぜ」を書く。「何をしているか」は書かない（コードを読めば分かる）
- UI文言はすべて日本語。ボタン・エラーメッセージ・空状態のトーンをこのアプリと揃える（丁寧だが硬すぎない）
- 破壊的操作（削除等）は必ず確認ダイアログを挟む
- 楽観的更新は「失敗時に元に戻す」処理とセットで実装する
- 型は明示的に。`any` を使わない
